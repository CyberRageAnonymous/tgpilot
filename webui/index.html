About

tgpilot is a free, open-source tool for Telegram Serverless bots: write the code in a plain folder and deploy, run, migrate and keep an eye on it — from the terminal or from this studio. Everything stays on your machine; the bot token never leaves it. Made with care by the CyberRage team.

Remote servers

On a remote machine there is usually no proxy running on it. Either start one there, or tunnel your own machine's proxy through SSH: ssh -R 10809:127.0.0.1:10809 user@server — then use socks5://127.0.0.1:10809 here.

tgpilot in one minute

tgpilot runs your Telegram Serverless bot from a plain folder. You write JavaScript, the cloud runs it — no server to keep alive, no deploy pipeline to babysit. Everything stays on this machine; the bot token never leaves it.

Three ways to work with it: the studio in the browser (this one), the terminal (tgpilot help lists every command), and the files themselves — the studio edits the very files you would edit by hand.

Getting started

  1. Link a bot. Open @BotFather, pick your bot, go to Serverless → CLI Access and copy the access token. Paste it in the Link panel in the corner.
  2. Add a handler. Every update type is a function. Open Handlers, press + module and pick the update you want to react to.
  3. Try it without deploying. Run in the editor calls the cloud with a sample payload and shows the live logs.
  4. Deploy. Deploy & status → Review changes shows what will go up; confirm and it is live.

The project layout

mybot/
├── tgcloud/
│   ├── handlers/     one file per update type (message.js, callback_query.js…)
│   ├── endpoints/    functions your Mini App can call
│   ├── lib/          shared modules you import
│   └── schema.js     the tables and columns of your database
├── dist/             the Mini App build (optional)
└── tgcloud.jsonc     the project settings

Only handlers/ and endpoints/ run in the cloud; lib/ is imported by them, and schema.js describes the database. Everything else in the folder is yours — the studio shows it under Other files and never deploys it.

Handlers, endpoints and the database

A handler is one file per update type:

export default async function (message, ctx) {
  await ctx.send('hello');
}

An endpoint is a function your Mini App can call over HTTP. schema.js describes your tables; changes to it become migrations you review and apply in the Database section.

Backups

Save a copy of the project before a big change. If the bot breaks, restore the copy with one click — the state at that moment is saved as a backup of its own, so a restore can never destroy work.

In the terminal: tgpilot backup, tgpilot backups, tgpilot restore <id>.

Several bots in one folder

A folder can be linked to more than one bot — a staging copy next to the live one. Press the bot name in the top bar to link, switch or remove a profile.

In the terminal: tgpilot login --profile staging <token>, tgpilot profiles, tgpilot profiles --use staging.

When the cloud cannot be reached

The Network card on the home page says how this machine reaches the cloud: the proxy that is running, the DNS answer and the route. If telegram.org is blocked on your network, point tgpilot at a proxy — HTTP or SOCKS5, the kind is detected on its own:

export TGPILOT_PROXY=socks5://127.0.0.1:10808
tgpilot ping

Add the same address in the Network card and it is stored with the project. A filtered DNS can be worked around with DNS over HTTPS (TGPILOT_DOH=1).

The terminal

The studio is one way in; the terminal is the other. The most useful commands:

  • tgpilot status — what differs from the bot
  • tgpilot diff — the changes, line by line
  • tgpilot push — deploy the changes
  • tgpilot run message '{"text":"hi"}' — run a handler in the cloud
  • tgpilot migrate — walk through the database changes
  • tgpilot webhook — the webhook state
  • tgpilot logs — the journal of this tool
  • tgpilot help — the full list

When something goes wrong

Errors in the studio come as a report: what happened, which file failed and a button that opens the file at the right line. The journal keeps the rest:

  • tgpilot logs — everything this tool did
  • tgpilot ping — is the cloud reachable at all
  • tgpilot status — does the folder still match the bot
  • tgpilot backup — save the state before trying something risky
